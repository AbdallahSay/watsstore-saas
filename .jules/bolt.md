## 2024-06-25 - ExecuteDeleteAsync execution order and FK constraints
**Learning:** When replacing `RemoveRange()` with EF Core's `ExecuteDeleteAsync()` for bulk deletes, you lose the Change Tracker's automatic topological sorting of `DELETE` statements. If the hardcoded execution order of `ExecuteDeleteAsync()` calls violates Foreign Key constraints (e.g. deleting a Product before an Order that references it, if such a relationship exists), it will throw a SQL constraint exception and rollback the transaction. Wait, the schema actually uses `ON DELETE CASCADE` for relations from `Store` to `WhatsAppOrder` / `Product` etc. The DB itself would handle the cascading if we just deleted the store. But since we are explicitly deleting each table using `ExecuteDeleteAsync`, the order might matter if there's a strict FK without cascade. Wait, checking `WhatsAppOrder`, it has no foreign key to `Product` at all (it stores a snapshot of the cart in a JSON column or similar, typically). We don't see any explicit FK between Product and Order or StoreReview and Product. So our `ExecuteDeleteAsync` order shouldn't hit FK violations. Still, order matters in general.
**Action:** Always verify schema foreign key constraints when converting to `ExecuteDeleteAsync()`. If there are dependencies, order the `ExecuteDeleteAsync` calls to delete dependent child entities first, then parent entities.
