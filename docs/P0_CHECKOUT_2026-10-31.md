# P0 checkout incident — 2026-10-31

## Root cause and reproduction

Production deployment `dpl_cq1KTLnNhdthCXar3nu8LMuAfnGN` (master `2316e3e`)
had no Vercel project environment variables. Catalog requests used api.ts's live
backend fallback, but commerce-api.ts independently fell back to
`http://localhost:5000/api`. At a 390×844 mobile viewport, confirming an A9 cart
sent POST to `http://localhost:5000/api/public/stores/a9/orders` and failed with
`net::ERR_CONNECTION_REFUSED`. Safari's reported “Load failed” is consistent with
that transport failure; native Safari reproduction is unavailable on this host.
Tracking and merchant commerce settings shared the same incorrect fallback.

The captured attempt used one dedicated test identity and a retained idempotency
key. A parameterized production database query found zero orders for that key;
A9's total remained two. An older order exists, but cannot be attributed to the
user's earlier failed session without its request key. No uncertain production
transaction was blindly retried.

## Excluded causes

- Exact live orders OPTIONS: 204, correct production Allow-Origin, Allow-Methods
  POST and Allow-Headers content-type. No redirect.
- Non-creating invalid JSON-body POST: 400 with readable validation and CORS.
  IIS accepts OPTIONS, POST and the actual JSON content-type header.
- Database schema has all commerce/order fields, identity OrderNumber, and
  history tables. A9 products are available, have no variants, and have no tracked
  inventory rows. No inventory checks were disabled.
- IIS stdout was temporarily enabled using existing FTPS access and restored.
  No backend exceptions were logged during the captured failed submission because
  it never reached IIS. Oversized bodies were not used to flood production; the
  actual checkout request is small and this failure occurs before body handling.

## Fix

- Catalog, checkout, tracking and Open Graph use one API base module and the same
  live HTTPS fallback. Hosted builds reject insecure/loopback overrides.
- Vercel production NEXT_PUBLIC_API_URL explicitly configured to the live backend.
- Arabic network/validation errors, bounded request timeout and redirect rejection.
- Customer details persist across uncertain outcomes and reloads. A pending attempt
  freezes its original payload and key; explicit retries reuse both. Double clicks
  are guarded. Old-format saved attempts are recovered with their original keys.
- Session persistence is required before sending; no unrecoverable-key submission.
- Only explicit HTTP validation rejection allows corrected data to receive a new key.
- No production backend binaries or database migration are needed for this frontend
  configuration defect. Authentication, tenant isolation, inventory and payment
  validation remain unchanged.

## Local validation

- Backend: 11 integration tests pass, including exact orders CORS preflight,
  validation, success, idempotent replay and conflict responses.
- Frontend: 8 regression tests pass; TypeScript and Next.js production build pass.
- Browser: Chrome at 390px, 375px and 1440px passes. Uses an isolated API/SQLite
  database, real controllers and merchant JWT authentication; no mock order API.
  Lost response AFTER commit → reload → same-key replay gives exactly one order
  and one stock deduction, with merchant visibility and redacted public tracking.
- Existing NuGet dependency advisories remain warnings in the baseline; this fix
  does not modify backend dependencies or deploy backend binaries.
